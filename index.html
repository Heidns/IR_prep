Introduction & basic concepts

CO1Lec 1–2

Core definitions

  • IR: the organisation, storage, retrieval and evaluation of information relevant to a user's need (the query).
  • An IR system returns documents that contain the information, not the information itself. It "informs on the existence and whereabouts of documents."
  • Document: any retrievable unit (PDF, email, web page, post).
  • Collection / corpus: the set of documents searched.
  • Query: the information need as the user expresses it. Types: keyword, natural language, Boolean, phrase.

IR process (6 steps)

  1. User enters a query through the UI
  2. The query is processed and refined
  3. Documents are preprocessed and indexed
  4. The processed query is matched against the index
  5. Matches are ranked by relevance
  6. Ranked results are displayed

Components: user · query · document collection · index · search engine · ranking module · results.

Structured vs semi-structured vs unstructured

StructuredSemi-structuredUnstructured
Tables, DB records, CSV, ExcelXML, HTML, JSON, metadata, medical recordsFree text, PDF, images, web page text
Exact-match and range queries: Salary < 60000 AND Manager = SmithFlexible schema, tags, hierarchy, field-specific searchKeyword queries with operators, "concept" queries

IR vs. DBMS: a DBMS works on structured data with a fixed schema. Queries (SQL) are exact, results are exact sets and unranked, and a result is correct or incorrect. IR works on unstructured text. Queries are vague natural language, results are ranked by relevance, and a result is judged relevant or not relevant. Most IR systems deal with unstructured documents.

IR model

An IR model has four parts: a document representation, a query representation, a matching function and a ranking function. Documents are usually represented as a set of index terms, not their raw text. The three classical models are Boolean, vector space and probabilistic. A fourth, the language model, scores a document by the probability that it would generate the query. If a question asks for "four models", give Boolean, vector space, probabilistic and language model; if it says "classical", give the first three.

Why index at all? Grepping is slow on large corpora, handles NOT badly, can't do proximity (Romans NEAR countrymen) and can't rank. Indexing turns the text into a representation, most commonly an inverted index, ahead of time. It is an offline operation: it runs once, before any user searches, and is redone only when documents change. Shakespeare's collected works are under a million words, so grepping them is tolerable; a billion web pages of a thousand words each are not.

Relevance, and what users actually want

A document is relevant if it satisfies the user's information need. Four factors decide it: topicality (is it about the right subject?), freshness (how current is it?), authority (.gov, .edu, IEEE, ACM, WHO vs an unknown blog) and fit to need ("Python tutorial for beginners" should not return advanced material). Since many documents are relevant, the system ranks them.

Three types of information need

  • Known-item search — the user knows the exact document and wants its location: "C Programming Language by Dennis Ritchie".
  • Precise-information search — the user wants one fact, not a document: "Capital of Japan", "What is TCP/IP?"
  • Open-ended (topical) search — the user wants to explore a subject and many documents will do: "Artificial Intelligence".

Scarcity vs abundance

  • Information scarcity — the needle-in-a-haystack problem. One rare document holds the answer: "Who won the 1995 gold medal at XYZ University?" This is a recall problem.
  • Information abundance — thousands of near-identical documents: "What is toxoplasmosis?" The hard part is picking the most reliable one. This is a precision and ranking problem.

Measuring performance: precision and recall

Formulas

  • Precision = (relevant ∩ retrieved) ÷ retrieved. "Of what I returned, how much was useful?" Measures accuracy.
  • Recall = (relevant ∩ retrieved) ÷ all relevant. "Of what was useful, how much did I find?" Measures completeness.
  • Both lie in [0,1]; higher is better on each.

Worked example verified

  • Relevant in collection = 50, retrieved = 15, relevant among retrieved = 12.
  • Precision = 12/15 = 0.80 (80%)
  • Recall = 12/50 = 0.24 (24%)
  • Reading: most of what came back was useful, but three-quarters of the good documents were missed.

Neither works alone, because each is trivially maximised by wrecking the other:

StrategyPrecisionRecallWhy it's useless
Return every document (1000 docs, 20 relevant)20/1000 = 2%20/20 = 100%The user wades through 980 irrelevant hits
Return one document, and it is relevant1/1 = 100%1/20 = 5%Accurate but 19 relevant documents are missed
Balanced systemHighHighThe actual goal

A one-line extra if you want it: F₁ = 2PR/(P+R) combines the two. For P = 0.80, R = 0.24 that is 0.369, which punishes the low recall in a way an arithmetic mean (0.52) would hide. F₁ is not on either slide set, so offer it as an aside, not as the answer.

IR beyond text: similarity search

IR over images, audio, video and faces compares features — colour, shape, texture, pitch, rhythm, motion — instead of words. TinEye does reverse image search; Shazam identifies a song from a ten-second recording.

A · 2Differentiate structured and unstructured data with an example query of each.

Structured data sits in tables with a fixed schema and supports exact and range queries, e.g. Salary < 60000 AND Manager = Smith. Unstructured data is free text with no schema. It is searched with keyword or concept queries, e.g. "pages about drug abuse", and results are ranked by relevance.

A · 2What are the components of an IR model? Name the three classical models.

The components are a document model, a query model, a matching function and a ranking function. The classical models are Boolean, vector space and probabilistic.

B · 4Why is linear scanning (grep) inadequate for IR? How does indexing help?
  • It is slow: every query touches the whole corpus, so cost is O(corpus size).
  • NOT is non-trivial.
  • It can't do proximity queries.
  • It can't rank results.

Indexing preprocesses documents once into an inverted index (term → sorted docIDs). A query then touches only the postings of its terms, which supports fast Boolean merges, positional queries and scoring.

A · 2Define precision and recall. A system retrieves 15 documents, 12 of which are relevant, out of 50 relevant documents in the collection. Compute both.

Precision = relevant retrieved ÷ retrieved = 12/15 = 0.80. Recall = relevant retrieved ÷ total relevant = 12/50 = 0.24. Precision measures the accuracy of the result set; recall measures its completeness.

B · 4Why can a system not simply maximise both precision and recall? Illustrate.

They trade off. Take 1000 documents with 20 relevant.

  • Return all 1000: recall = 20/20 = 100%, precision = 20/1000 = 2%. Perfect recall, useless result set.
  • Return a single relevant document: precision = 1/1 = 100%, recall = 1/20 = 5%. Perfect precision, 19 relevant documents missed.

Each is trivially maximised by degrading the other, so a useful system sits between them. F₁ = 2PR/(P+R) is the usual single-number summary.

Boolean retrieval model

CO1Lec 3–4
  • The oldest classical model, based on Boolean logic and set theory. A document is a set of keywords.
  • A query is a Boolean expression using AND, OR and NOT. Retrieval is exact match: a document either satisfies the query or it doesn't, and nothing is ranked.
  • 1 = the term is present in the document, 0 = absent (Boole's two-valued logic). AND narrows (all terms required), OR broadens (any term), NOT excludes. Truth values: A∧B is 1 only for 1,1; A∨B is 0 only for 0,0; ¬A flips. Parentheses control evaluation order: (AI OR ML) AND Python evaluates the OR first.
  • Term-document incidence matrix: rows are terms, columns are documents, and a cell is 1 if the document contains the term.

Worked: Brutus AND Caesar AND NOT Calpurnia

Documents in order: Antony&Cleopatra, Julius Caesar, Tempest, Hamlet, Othello, Macbeth.

Brutus          110100
Caesar          110111
Calpurnia       010000  → complement 101111
AND             100100  → Antony & Cleopatra, Hamlet

The slide example (Antony ∧ Caesar) ∧ ¬Brutus returns only Macbeth.

Why the matrix fails at scale

N = 1M docs × ~1K terms each → 10⁹ tokens (~6 GB of text)
M = 500K distinct terms → matrix = 500K × 1M = 5×10¹¹ cells
At most 10⁹ ones → ≥ 99.8% zeros → extremely sparse → store only the 1s = inverted index

Advantages

  • Simple, precise, predictable
  • Easy to implement with set operations
  • Professionals like it (e.g. Westlaw legal search, which has used Boolean since 1975)

Limitations

  • No ranking: feast or famine (AND returns too few, OR too many)
  • Users must write precise expressions, and complex queries are hard for ordinary users to write
  • Ignores term frequency and importance, so no partial relevance
  • No awareness of synonyms or meaning
  • Without an index it scans every document: O(N×M)

Applications: digital libraries and library catalogues, research-paper and patent databases, legal search, medical literature search, enterprise search. These are domains where users are trained, want reproducible result sets, and need to be sure nothing was silently dropped by a ranker.

B · 3Given an incidence matrix, evaluate (A OR B) AND NOT C.

Method: write each term's bit-vector. OR the vectors for A and B. Complement C. AND the results. Read off the documents with a 1. Show every intermediate vector: that is where the marks are.

A · 2Why is the term-document matrix impractical for large collections?

It is huge (500K × 1M = 5×10¹¹ cells) and extremely sparse (at most 10⁹ ones, so at least 99.8% zeros). Storing only the 1s, as an inverted index, is far more compact.

Inverted index & processing Boolean queries

CO1CO2Lec 5–6 + skip-pointer reading

Inverted index: a dictionary of terms, each with its document frequency (df), its collection frequency (cf, total occurrences across the collection) and a pointer to a postings list of docIDs sorted by docID. Each docID in the list is a posting. Linked lists allow easy insertion but cost pointer overhead. Arrays are compact but hard to update.

Forward indexInverted index
DirectionDocument → wordsWord → documents
Answers"What words are in this document?""Which documents contain this word?"
ExampleD1 → {Machine, Learning}Learning → {D1, D2, D3}
RoleWhat parsing produces firstWhat queries actually search

The book analogy: the forward index is a page (page 1 contains Machine, Learning, AI); the inverted index is the index at the back (Learning → pages 1, 2). The term-document matrix of Unit 2 stores both directions and is almost all zeros, which is why only the 1s are kept.

Construction (Indexer steps)

  1. Tokenize, then apply linguistic modules (normalize, stem): Friends Romans Countrymen → friend roman countryman
  2. Emit (term, docID) pairs
  3. Sort by term, then docID. This is the core indexing step
  4. Merge duplicate entries in the same document and add frequency
  5. Split into a Dictionary file (term, df, pointer) and a Postings file

Merge algorithms: O(x + y)

INTERSECT(p, q)                     UNION(p, q)
  answer ← ()                         while p ≠ nil and q ≠ nil
  while p ≠ nil and q ≠ nil             if docID(p) = docID(q): out p; advance both

       add docID(p); advance p, q       else: out q; advance q
    elif docID(p) < docID(q): advance p  output remaining of p, then of q
    else advance q
  return answer

AND NOT (p, q): walk both; output docID(p) only when it is not in q.

All of these depend on the postings being sorted by docID.

Query optimization

  • For an AND of t terms, process terms in increasing df: start with the smallest set and keep cutting. This is why df is stored in the dictionary.
  • Slide example: Brutus (7), Calpurnia (8), Caesar (2) → execute (Caesar AND Brutus) AND Calpurnia.
  • For (madding OR crowd) AND (ignoble OR strife), estimate each OR's size as the sum of its dfs (a conservative upper bound), then process the ORs in increasing size.

Skip pointers

  • Skip pointers are added at indexing time. They let an AND intersection jump past postings that can't match, giving sublinear behaviour in practice.
  • Placement heuristic: √P evenly spaced skips for a list of length P.
  • Trade-off: more skips means short spans, so skips are taken often, but there are more comparisons and more storage. Fewer skips means long spans, which are rarely usable.
  • Skips help only AND, not OR, because a union must visit every posting anyway. Intermediate results have no skips. Skips are easy on a static index and hard under frequent updates. On modern hardware they help less, because loading bigger postings can cost more than the in-memory merge saves.

Phrase and proximity queries

Biword index

  • Index every consecutive pair of terms: "friends romans", "romans countrymen".
  • A longer phrase becomes an AND of biwords (stanford university AND university palo AND palo alto), which needs post-filtering and can give false positives.
  • Extended biwords: POS-tag the text, then treat any N X* N sequence as one term (king of Denmark, catcher in the rye).
  • Rarely used, because false positives and vocabulary blow-up.

Positional index

  • Each posting is docID: ⟨pos1, pos2, …⟩.
  • Answers phrases exactly and supports proximity (employment /4 place = within 4 words; Westlaw also uses /s same sentence and /p same paragraph, alongside & for AND, | for OR, % for NOT and " " for a phrase).
  • Takes much more space (2–4× a non-positional index) and costs more per query.
  • Combination scheme: store frequent phrases (Michael Jackson) as biwords and handle all other phrases positionally.

A · 2Boolean AND vs the proximity operator.

AND needs both terms to appear anywhere in the document and ignores order and distance. Proximity (NEAR/n) needs them within n words, which gives more precise, context-specific results but requires positional postings.

B · 5Write the intersect algorithm and trace Brutus [2,4,8,16,32,64,128] AND Caesar [1,2,3,5,8,13,21,34]. What is its complexity?

2 vs 1 (advance Caesar), 2=2 is added. Then 4 vs 3 (advance Caesar), 4 vs 5 (advance Brutus), 8 vs 5, 8 vs 8 is added, 16 vs 13, 16 vs 21, 32 vs 21, 32 vs 34, 64 vs 34, and Caesar ends. Answer {2, 8}. The cost is O(x + y) because each comparison advances at least one pointer, and it depends on the lists being sorted by docID.

A · 2Distinguish a forward index from an inverted index.

A forward index maps document → words and answers "what words are in this document?" (D1 → Machine, Learning). An inverted index maps word → documents and answers "which documents contain this word?" (Learning → D1, D2, D3). The forward index is what parsing produces; the inverted index is what queries search, because it lets a query touch only the postings of its terms instead of every document.

B · 4Compare term-at-a-time and document-at-a-time query processing.

TAAT processes one term's entire postings list, accumulating partial scores in an accumulator array, then moves to the next term. It is simple, but every candidate document must stay in memory and no score is final until the last term is done.

DAAT advances all postings lists together in docID order and completes one document's score before moving on. It needs less memory and, crucially, a document's score is final as soon as you pass it — which is what makes dynamic pruning (WAND) and early termination possible. Modern engines prefer DAAT for exactly this reason.

C · 6Discuss the techniques used for query optimisation in an IR system.

Lead with the one that carries the marks, then give breadth:

  1. Order postings by size — process terms in increasing df so intermediate results stay small. A = 10,000, B = 500, C = 20 postings → evaluate (C ∩ B) ∩ A, not (A ∩ B) ∩ C.
  2. Skip pointers — √P evenly spaced pointers let the merge jump past postings that cannot match.
  3. Boolean re-association — (A AND B) AND C ≡ A AND (B AND C); choose the cheaper grouping.
  4. Query rewriting — synonym expansion to raise recall.
  5. Caching of frequent queries.
  6. TAAT vs DAAT — DAAT is preferred because a score completes as you pass the document, which enables ranking and pruning.
  7. Dynamic pruning — WAND and Block-Max WAND skip documents that cannot enter the top-k.
  8. Early termination — stop once the top-10 is settled.

Document & term processing

CO1CO2Lec 7–9

Document delineation

Document delineation finds the boundaries of individual documents in a collection — where one document ends and the next begins — and gives each a docID. It runs before document processing. Part of it is settling the format (pdf, docx, html), the language and the character encoding; each is a classification problem, usually solved with heuristics. The rest is choosing the document unit: a file, an email, an email with 5 attachments, a group of files. There is no single right answer; it is a design decision.

Three kinds

  • Physical — explicit markers: <doc>…</doc> tags, page breaks, chapter breaks, file boundaries.
  • Logical — inferred from content structure: headings, titles, sections, paragraph patterns.
  • Automatic — ML/NLP boundary detection, for crawled pages, email threads, news archives, social media and OCR scans.

Delineation vs processing

DelineationProcessing
PurposeFind document boundariesPrepare a document for indexing
InputA collection or raw streamOne individual document
OutputSeparate documents with docIDsProcessed index terms
OrderFirstSecond

The pipeline to draw: collection → delineation → individual documents → processing (tokenise, stop words, normalise, stem) → index construction → search.

Granularity and passage retrieval

Indexing a 400-page book as one document causes dilution: a high tf for the query term is washed out by thousands of unrelated terms, and the user wanted the paragraph, not a 400-page PDF. Fine granularity (sentences) gives precise matches but loses context; coarse granularity (sections, pages) keeps context but adds noise. The fixes are chunking (cut text into blocks before indexing), static passage retrieval (uniform pre-cut chunks, e.g. 256–512 tokens with ~10% overlap, or logical sections), dynamic passage retrieval (a sliding window scoring term density around query hits at query time) and TextTiling, which detects topic shifts as dips in block-based cosine similarity between adjacent token sequences.

Ingestion details

  • Encoding: normalise ASCII, UTF-16 and ISO-8859-1 input into UTF-8. Unicode has two normal forms — NFD decomposes é into e + a combining acute accent, NFC recomposes it. Pick one before you sort or compare terms.
  • HTML/XML stripping: replace block tags with newlines, or </h1>Content merges into a junk term like HeaderContent.
  • OCR noise: scanning confuses cl→d and rn→m, which is exactly what the tolerant retrieval of Unit 5 has to repair.

A · 2"In June, the dog likes to chase the cat in the barn." How many tokens and how many types?

12 tokens. Types: 10 without case folding (In and in differ, and "the" is counted once), or 9 with case folding. State your assumption.

Tokenization issues

  • Apostrophes: O'Neill, aren't, India's. Hyphens: Hewlett-Packard, state-of-the-art, co-education. Multi-word names: San Francisco, New Delhi, York University vs New York University.
  • Numbers and dates: 3/20/91, 20/3/91, Mar 20 1991, B-52, IP addresses, phone numbers. These are often indexed separately as metadata.
  • Languages: Chinese and Japanese have no spaces, and segmentation can be ambiguous. German and Dutch have compounds (Lebensversicherungsgesellschaftsangestellter), handled by a compound splitter. Arabic and Urdu are bidirectional. French elision (L'ensemble).

Normalization

  • Equivalence classing: U.S.A. = USA, résumé = resume, Universität = Universitaet. The main criterion is how users are likely to type their queries.
  • Asymmetric expansion: the query window searches window and windows; windows searches Windows and windows; Windows searches Windows only. This is more powerful but less efficient.
  • Case folding: lowercase everything. It fails for MIT/mit, Fed/fed, SAIL/sail and General Motors, but users type lowercase anyway.
  • Stop words (a, the, of…): the top 30 words are about 30% of postings and carry little meaning. The trend is not to remove them, because you need them for phrases ("King of Denmark", "President of India"), titles ("Let it be", "To be or not to be") and relational queries ("flights to Bangalore"). Most web engines index them.
  • Thesauri (car = automobile, semantic equivalence) and Soundex (phonetic equivalence) handle this by expanding either the index or the query.

It hurts [operational AND research], [operating AND system] and [operative AND dentistry], because Porter maps operate, operating, operational and operative all to oper. Two named error types: over-stemming (a false positive) conflates unrelated words to one root — organization and organ both → organ, and likewise university→universe, policy→police — and hurts precision; under-stemming (a false negative) leaves forms of the same word apart — european and europe do not merge — and hurts recall. A stemmer is tuned to trade one against the other.

Morphological processing is the principled version: analyse a word into prefix + root + suffix. unhappiness → un + happy + ness; rewriting → re + write + ing. It lets compute, computer, computing, computation, computational all reach compute, and it is the distinction behind inflectional (cutting→cut) vs derivational (destruction→destroy) morphology above.

Porter stemmer

  • Five phases applied in sequence, each a set of condition → action rules. Within a compound command, the rule matching the longest suffix wins, and only one rule per step fires.
  • Measure m: the number of VC sequences in [C](VC)m[V]. tree m=0, trees / oak m=1, private m=2.
  • Conditions: *S (stem ends in S), *v* (stem contains a vowel), *d (stem ends in a double consonant).

B · 4Should a modern search engine remove stop words? Justify.

Removing them used to be standard because stop words take about 30% of postings and carry little meaning. Modern engines keep them for phrase queries ("King of Denmark"), titles ("To be or not to be") and relational queries ("flights to Bangalore"). Compression and good query optimization (process rare terms first, impact ordering) keep the cost down.

B · 4What is document delineation? Name its three types and say how it differs from document processing.

Document delineation identifies the boundaries of individual documents in a collection — where one ends and the next begins — and assigns each a docID. Three types: physical (explicit markers such as <doc> tags, page or file breaks), logical (inferred from headings, titles, sections) and automatic (ML/NLP boundary detection, used for crawled pages, email threads and OCR scans).

It differs from document processing in purpose, input and order: delineation takes the whole collection and outputs separate documents, and runs first; processing takes one document and outputs index terms via tokenisation, stop-word removal, normalisation and stemming.

Dictionaries & tolerant retrieval

Dictionary search structures

Lec 10 has no slides among your uploads, so this part is from Manning §3.1.

Hash table

  • O(1) lookup
  • Collisions need handling
  • No prefix search: automat* is impossible, and minor variants (resume/résumé) hash to unrelated slots
  • Must be rehashed as the vocabulary grows

Search tree (binary / B-tree)

  • O(log M) lookup, which requires a balanced tree
  • Supports prefix and range queries
  • A binary tree needs rebalancing
  • A B-tree lets each internal node have between a and b children (e.g. [2,4]). It collapses levels, suits disk blocks, and rebalances less often
  • Needs a total ordering of characters

Trie / TST / FST

  • Trie (or ternary search tree): characters branch from the root, and a marked node ends a term. Lookup is O(term length) and prefix search is native, so it is the best structure for comput*
  • FST / DAWG: a directed acyclic graph that shares both prefixes and suffixes, so it is very compact and still prefix-friendly. This is what Lucene actually uses
  • A sorted array is the simple middle ground: O(log N) binary search and prefix-friendly, but costly to insert into

The examinable trade-off is the hash table against everything else: hashing is fastest for exact lookup but cannot enumerate a prefix, which is why tolerant retrieval needs a tree or trie.

Wildcard queries

  • Trailing mon*: use a B-tree and take all w with mon ≤ w < moo. The matches are contiguous.
  • Leading *mon: use a reverse B-tree (terms spelled backwards): nom ≤ w < non.
  • Middle se*tic: B-tree(se*) ∩ reverse-B-tree(*tic).
  • General (multiple *): use a permuterm index or a k-gram index, then post-filter, then look up the surviving terms in the inverted index.

Permuterm index

Add $ to the end of each term and index every rotation. hello gives hello$, ello$h, llo$he, lo$hel, o$hell, $hello, which is m+1 rotations for m letters. Every rotation points to hello. To answer a query, rotate it so the * is at the end, then do a prefix lookup.

k-gram index

Index every k-character sequence of each term, with $ at the boundaries, and map each k-gram to the terms that contain it. Bigrams of april: $a ap pr ri il l$.

  • mon* → $m AND mo AND on. red* → $r AND re AND ed, which also matches retired, so you must post-filter.
  • Compared with permuterm: it takes less space, but you have to generate candidates and then filter them.

Spelling correction

  • Two uses: correcting documents (e.g. OCR errors like O/D, r/n) and correcting queries ("Did you mean…").
  • Isolated-word correction checks each word alone, so it misses form typed for from. Context-sensitive correction looks at the surrounding words ("flew form Heathrow").
  • The lexicon can be a standard dictionary, a domain lexicon, or the corpus's own vocabulary.
  • Closeness is measured by edit distance, weighted edit distance or k-gram overlap (Jaccard).

C · 6Compare the permuterm and k-gram indexes for m*n and fi*mo*er.

Permuterm: m*n → n$m*, a single prefix lookup. fi*mo*er → er$fi*, then post-filter the candidates for "mo" in the right place.

Bigram: m*n → $m AND n$, then post-filter. fi*mo*er → $f AND fi AND mo AND er AND r$, then post-filter (e.g. fishmonger passes; a term matching the bigrams in the wrong order fails).

Permuterm is faster but uses about 4× the dictionary. k-gram uses less space but needs a generate-then-filter step.

A · 2Why can't a hash table serve wildcard queries?

Hashing scatters lexically adjacent terms, so there is no way to enumerate all terms with a prefix. A B-tree keeps terms in order, so a prefix is a contiguous range; a trie or FST goes further and makes the prefix a path from the root.

B · 3Why is *ing hard on a normal B-tree, and how do you fix it?

The B-tree orders by the start of the word, so words ending in ing (computing, reading, running) are scattered. Fix it with a reverse B-tree (look up gni*) or permuterm (ing$*).

Index construction

CO2Lec 13–16

Hardware basics

  • Disk is about 10⁶× slower than RAM, so keep hot data in memory (caching).
  • Memory hierarchy: registers → cache (SRAM) → DRAM → disk/SSD → tape.
  • Parameters: seek s = 5 ms, transfer b = 0.02 µs/byte, CPU op p = 0.01 µs. Access time = seek + rotational latency + transfer.
  • The OS reads whole blocks (8–256 KB), so reading 1 byte costs as much as a block. Use buffers. Reading compressed data and decompressing it is faster than reading raw data.
10 MB contiguous: 10⁷ × 2×10⁻⁸ s + 1 seek = 0.2 + 0.005 = 0.205 s
10 MB in 100 chunks: 0.2 + 100 × 0.005 = 0.7 s (≈3.4× slower)

RCV1: N = 800K docs, Lavg = 200 tokens, M = 400K terms, T = 100M tokens, about 1 GB of text. At 8 bytes per (termID, docID) pair, T × 8 = 800 MB of intermediate data. That doesn't fit in RAM, so external sorting is needed. TermIDs (4 bytes, fixed length, one-instruction comparisons) are used instead of strings (about 7.5 bytes and variable length).

BSBI: Blocked Sort-Based Indexing

BSBI(collection)
  n ← 0
  while (docs remain)
     n ← n+1
     block ← PARSENEXTBLOCK()          // (termID, docID) pairs until the block is full
     BSBI-INVERT(block)                // sort pairs in memory, group into postings
     WRITEBLOCKTODISK(block, fₙ)
  MERGEBLOCKS(f₁…fₙ ; f_merged)        // k-way merge with a min-heap
  • Complexity Θ(T log T) because of sorting, but in practice parsing and merging (I/O) dominate.
  • The merge opens all block files with read buffers, keeps a min-heap on the current smallest termID from each file, pops it, concatenates that term's postings from all blocks, and writes through a write buffer. Each heap operation is O(log n).
  • Limitation: it needs a global term→termID map in memory.

SPIMI: Single-Pass In-Memory Indexing

  • Uses the term string as the hash key and appends the docID directly to that term's postings list, so there are no (termID, docID) pairs and no global termID map.
  • Postings lists are dynamic arrays that double when full (amortized O(1) per insert).
  • When memory is full, it sorts the terms (not the pairs) and writes the block. Blocks are merged as in BSBI.
  • Θ(T): linear, and faster.

Dynamic indexing

  • Auxiliary index: a big main index on disk plus a small auxiliary index in RAM for new documents. A query searches both and merges the results. Deletions go in an invalidation bit vector, and results are filtered through it. An update is a delete plus a re-insert.
  • Merging the auxiliary index into the main one each time it reaches n postings costs Θ(T²/n), which is quadratic.
  • Logarithmic merging keeps indexes I₀, I₁, … of sizes n, 2n, 4n, …. When Z₀ fills, it merges upward like a binary counter. Cost is Θ(T log(T/n)). The price is that a query has to search up to log(T/n) indexes. Lucene and Elasticsearch work this way.
  • Why not one file per postings list? File systems choke on millions of small files. One big file means rewriting everything on each merge.
  • Querying under logarithmic merging means searching Z₀ plus every surviving I₀, I₁, I₂ … and taking the union of their postings. That is log(T/n) indexes, in practice under 20, so it is manageable — and documents become searchable immediately after indexing.

Distributed indexing

  • Two ways to split an index across machines. Document partitioning: each machine holds a full index over a subset of documents, so every query goes to every machine and the results are merged. Simpler and resilient, and the usual choice. Term partitioning: each machine holds all postings for a subset of terms, so a query touches only the machines holding its terms, but multi-term queries have to ship large postings lists between machines.
  • MapReduce (Dean & Ghemawat 2004): a master assigns splits. Parsers (map) emit (term, docID) pairs partitioned by key range (a–f, g–p, q–z) into segment files — that is term partitioning. Inverters (reduce) each collect one key range, sort, and write postings.
  • Fault tolerance, since machines in a large cluster fail routinely: reassignment (if a parser dies the master gives its 64 MB split to another machine), immutable segment files (map output is read-only, so re-running a task is always safe — there are no partial writes to undo) and checkpointing of the map phase's state. This is what makes petabyte-scale indexing possible on cheap commodity hardware.

Security and access control lists

The structure

  • Scenario: enterprise search. Managers may see Salaries.pdf; interns may not.
  • Build a user–document access matrix: rows = users, columns = documents, cell (i,j) = 1 if user i may read document j.
  • Invert it per user into an ACL postings list: User_Alok → [doc5, doc7, doc9].
  • Note the symmetry with the term–document incidence matrix of Unit 2 — same object, different rows.

Query processing with ACLs

  1. Text search returns candidates, e.g. [doc5, doc6, doc9].
  2. Fetch the user's ACL list, e.g. [doc5, doc7, doc9].
  3. Intersect them → [doc5, doc9], using the same INTERSECT algorithm as an AND query.

Challenges: an administrator's ACL can cover millions of documents, making the intersection slow, and permissions change constantly, which is the dynamic-indexing problem again. Workaround: many systems check permissions at the file-system level during final retrieval instead.

B · 4Document partitioning vs term partitioning for a distributed index.

Document partitioning: each machine holds a complete index over a subset of documents. Every query is broadcast to every machine and the results are merged. Simple, resilient to a machine failing (you lose some documents, not some terms), and the usual choice in practice.

Term partitioning: each machine holds all postings for a subset of terms. A query touches only the machines that hold its terms, which sounds cheaper, but a multi-term query has to ship whole postings lists between machines to intersect them. Parametric/zone indexes, tf-idf & vector space scoring

CO3Lec 19–22

Why ranked retrieval

Boolean search is feast or famine: "standard user dlink 650" returns 200,000 hits, while adding "no card found" returns 0. Ranked retrieval takes free-text queries, gives each document a score in [0,1] and shows the top k. Large result sets stop being a problem, provided the ranking works.

Parametric & zone indexes

  • Parametric: structured metadata fields (author, year, language) with a small value set. Queries filter by exact field values (Author=Shakespeare AND Year=1601 → intersect the two field postings).
  • Zone: free-text regions (title, abstract, body). Encode the zone either in the dictionary (merchant.title → D1) or in the postings (merchant → D1.title, D1.body). The second keeps the dictionary smaller and makes weighted zone scoring easier.

Vector space model

Developed by Gerard Salton in the 1960s (the SMART system). The one-line motivation: Boolean asks "does this document match?"; the vector space model asks "how well does it match?"

  • Each document and query is a |V|-dimensional tf-idf vector. The space is very high-dimensional and sparse.
  • Euclidean distance is a bad idea: it is large between vectors of different lengths even when their term distributions match. Take d and d′ = d appended to itself: same content, large distance, angle 0.
  • Ranking by increasing angle is the same as ranking by decreasing cosine, because cosine is monotonically decreasing on [0°, 180°].
‖x‖₂ = √(Σ xᵢ²) unit vector = x / ‖x‖₂
cos(q,d) = (q · d) / (‖q‖ ‖d‖) = Σ qᵢdᵢ / (√Σqᵢ² · √Σdᵢ²)
For length-normalized vectors: cos(q,d) = q · d

Advantages of VSM

  • Ranked retrieval rather than a flat set
  • Partial matching: a document need not contain every query term
  • Similarity is a simple, efficient computation
  • Accepts free-text natural-language queries

Limitations of VSM

  • Very high dimensionality (|V| can be 400,000)
  • No semantics: car ≠ automobile
  • Assumes term independence — the bag-of-words assumption above — so relationships between words are ignored
  • Computationally expensive at scale

SMART notation ddd.qqq

The three letters are tf, df and normalization. tf: n natural, l 1+log tf, a augmented 0.5 + 0.5·tf/max tf, b boolean. df: n none, t idf, p prob-idf. normalization: n none, c cosine. The standard scheme is lnc.ltc: documents get log tf, no idf and cosine normalization; queries get log tf, idf and cosine normalization.

C · 6Worked (slides): SaS, PaP, WH with log-tf and no idf. Which pair is most similar, and why?

Counts: affection 115/58/20, jealous 10/7/11, gossip 2/0/6, wuthering 0/0/38. Log-tf: SaS (3.06, 2.00, 1.30, 0), PaP (2.76, 1.85, 0, 0), WH (2.30, 2.04, 1.78, 2.58). After normalizing: SaS (0.789, 0.515, 0.335, 0), PaP (0.832, 0.555, 0, 0), WH (0.524, 0.465, 0.405, 0.588).

cos(SaS,PaP) = 0.789×0.832 + 0.515×0.555 ≈ 0.94. cos(SaS,WH) ≈ 0.79. cos(PaP,WH) ≈ 0.69. SaS and PaP (both Austen) share the same term distribution. WH's weight is spread onto wuthering, which neither of the others contains.

A · 2Jaccard score of the query "ides of march" against D1 "caesar died in march" and D2 "the long march".

D1: ∩ = {march} = 1, ∪ = 6, so 1/6 ≈ 0.167. D2: ∩ = 1, ∪ = 5, so 1/5 = 0.2. D2 ranks higher only because it is shorter. That shows Jaccard's weaknesses: no tf, no idf, crude length normalization.

B · 4Why use cosine similarity rather than Euclidean distance? Include the d / d′ argument.

Euclidean distance depends on vector length, and long documents have long vectors. If d′ is d appended to itself, the content is the same but the distance is large. The angle between them is 0 (cosine 1). Cosine, the dot product of length-normalized vectors, measures the direction, i.e. the term distribution, so long and short documents become comparable.

A · 2Parametric vs zone index.

A parametric index covers structured metadata fields with a finite set of values (year, author), used for filtering. A zone index covers regions of arbitrary free text (title, abstract, body), used for region-specific search and for weighted zone scoring.

Slide errata & traps

These are places where a slide disagrees with the textbook or with its own arithmetic. If one comes up in the exam, show the working and state the convention you're using. That protects your marks whichever version the examiner expects.

BSBI block size. One slide says "limit the block to 1 GB (10 million pairs)". But 1 GB ÷ 8 B is 125M pairs, and with that many pairs RCV1 fits in a single block. The "10 blocks" answer only follows if a block holds 10M pairs, which is 80 MB. Use whatever block capacity the question gives.
Permuterm rotations. The slide lists 5 rotations for hello and leaves out $hello. The book (and the same slide's "m+1 rotations") gives 6.
Weighted zone example. The slide's match column (Title=yes, Author=no) doesn't fit D1's actual text for the query "Shakespeare". See the note in Unit 7.
Edit-distance pseudocode. The slide labels D[i-1,j] as "insert" and D[i,j-1] as "delete". Relative to transforming the source into the target, those labels are swapped. With unit costs the numbers come out the same, so just be consistent.
lnc.ltc wording. One slide line says the query uses "no normalization", but the c in ltc means cosine, and the worked table does normalize the query (0.34, 0.52, 0.78). Normalize.
Soundex variant. Your slides (and Manning) code h, w and y as 0, like vowels. The "official" American Soundex treats h and w differently, so some online calculators give different codes. Follow the slide table.
Porter 1c. "sky → ski" breaks the (*v*) condition. See Unit 4.
Edit distance for "aplpe". An exercise asks which of {apple, apply, applied, bat, batch, cat, catch} lie within edit distance 2 of aplpe, and answers {apple, apply}. Recomputed: under plain Levenshtein, apple = 2 but apply = 3, so only apple qualifies. The given answer holds only under Damerau–Levenshtein (which allows transposition), where apple = 1 and apply = 2. State which metric you are using — that is the marks-bearing distinction.
"Skip pointers give O(√n)." A complexity table lists skip-pointer intersection as O(√n). The √ belongs to the placement heuristic (√P evenly spaced pointers), not to the running time. Skips give a useful constant-factor, sublinear-in-practice speed-up, but the worst case is still O(x + y). Say "sublinear in practice, O(x+y) worst case".
