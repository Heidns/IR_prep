Introduction & basic concepts

CO1Lec 1–2

Information retrieval is the organisation, storage, retrieval and evaluation of information relevant to a user's need. The definition sounds abstract, so anchor it to one example and keep reusing it: a student types machine learning tutorial into a search box and gets back a ranked list of pages.

Two things in that sentence are easy to get wrong in an exam. First, an IR system does not hand you the information — it hands you documents that contain it. The classic phrasing is that an IR system "does not inform the user on the subject of her inquiry; it merely informs on the existence and whereabouts of documents relating to the request." Google does not answer "what is machine learning"; it points at ten pages that do. Second, the thing the user actually has in their head (the information need) is not the same as the thing they typed (the query). The need might be "I want to learn ML from scratch"; the query is three words. Every hard problem in IR lives in that gap.

Vocabulary, fixed once: a document is any retrievable unit — a PDF, an email, a web page, a tweet. A collection (or corpus) is the set of documents being searched — Google's index, a library catalogue, your company's Confluence. A query is the information need as typed. Relevance is whether a returned document actually satisfies that need.

How the pieces fit together

An IR system has two halves that run at completely different times, and keeping them separate is the single most useful mental model in this course.

The offline half is called indexing, and the fact that it is offline is the whole point: the expensive work of reading every document happens once, in advance, so that a query touches only a small lookup structure. Indexing is redone only when documents change.

Structured, semi-structured and unstructured data

IR exists as a separate field from databases because of what the data looks like.

StructuredSemi-structuredUnstructured

Semi-structured data is the middle case people forget: it has no rigid table, but tags, labels or metadata give it enough organisation that you can search particular fields. An XML article with <title>, <author> and <body> elements is the standard example — and it comes back in Unit 7 as zone indexing. Most IR systems deal with unstructured documents.

IR vs a DBMS, in one comparison. A database holds structured data with a fixed schema; its queries (SQL) are exact, its results are an unordered set, and an answer is simply correct or incorrect — SELECT * WHERE salary < 60000 either returns the right rows or there is a bug. IR holds unstructured text; its queries are vague natural language, its results are ranked by relevance, and an answer is judged relevant or not relevant — a matter of degree, and different users will disagree. That shift from "correct" to "relevant" is why ranking, evaluation and the whole second half of this course exist.

What an IR model is

An IR model is the blueprint for how a system represents things and decides what to return. It has four parts: a document representation, a query representation, a matching function that compares the two, and a ranking function that orders the matches. Note that the raw text of the document is never used at retrieval time — only some representation of it, most often a set of index terms.

Why we index instead of just searching the text

The obvious way to answer which Shakespeare plays contain Brutus and Caesar but not Calpurnia? is to read every play start to finish and check. That is a linear scan, or grepping. It works here — Shakespeare's collected works are under a million words — but it fails for four separate reasons as soon as the collection grows:

  1. It is slow. Every query costs O(size of the collection). A billion web pages of a thousand words each is 10¹² words to read, per query.
  2. NOT is awkward. To exclude Calpurnia you must scan the document anyway just to prove the word is absent, so the exclusion saves you nothing.
  3. Proximity is impossible. "Find Romans near countrymen" needs to know where words sit, which a line-by-line scan discards.
  4. You cannot rank. Grep gives you matches, not a best-first ordering, and with a million matches an unordered list is useless.

Indexing fixes all four by paying the cost once, in advance, and storing a representation built for lookup. That representation is almost always the inverted index of Unit 3.

Relevance, and what users actually want

A document is relevant if it satisfies the user's information need — not merely if it contains the query words. For the query symptoms of dengue fever, a page on dengue symptoms is relevant, the current WHO dengue guidelines are highly relevant, and a page on malaria symptoms is not relevant even though it shares most of its vocabulary. Four factors decide it:

  1. Topicality — is it actually about the subject? (Machine Learning yes, Web Development no.)
  2. Freshness — for "latest AI tools in 2026", a 2026 article beats a 2018 one.
  3. Authority — .gov, .edu, IEEE, ACM, WHO over an unknown blog.
  4. Fit to the need — "Python tutorial for beginners" should not return an advanced text, even though it is on topic.

Because many documents will be relevant to some degree, the system must rank them rather than just return a set. That is the whole reason Unit 7 exists.

Three types of information need

  • Known-item search — the user already knows the exact document and only wants its location. "C Programming Language by Dennis Ritchie", "Python Notes Unit 1 PDF".
  • Precise-information search — the user wants one fact, not a document. "Capital of Japan", "Who invented Python?", "What is TCP/IP?"
  • Open-ended (topical) search — the user wants to explore, and there is no single right answer. "Artificial Intelligence", "Cyber Security". Many documents satisfy it.

Two opposite failure modes

  • Information scarcity — the needle in a haystack. "Who won the 1995 gold medal at XYZ University?" One rare document holds the answer and it is buried under thousands of irrelevant ones. This is a recall problem.
  • Information abundance — too much of the same thing. "What is toxoplasmosis?" returns thousands of near-identical explanations. Finding one is trivial; picking the most reliable is the work. This is a precision and ranking problem.

Measuring performance: precision and recall

Once results are ranked rather than simply correct, you need a way to say how well the system did. Both measures compare the same two sets — the documents the system retrieved and the documents that are actually relevant — and the only difference between them is which set goes in the denominator.

Precision

relevant ∩ retrieved ÷ retrieved

"Of what I returned, how much was useful?" Measures accuracy. Low precision means the user wades through junk.

Recall

relevant ∩ retrieved ÷ all relevant

"Of what was useful, how much did I find?" Measures completeness. Low recall means good documents were silently missed.

Why you need both. Each one alone is trivially gamed, which is the point the slides are really making:

StrategyPrecisionRecallWhy it's useless
Return every document (1000 docs, 20 relevant)20/1000 = 2%20/20 = 100%Perfect recall, but the user sifts 980 irrelevant hits
Return one document, and it is relevant1/1 = 100%1/20 = 5%Perfectly accurate, but 19 relevant documents missed
A real systemHighHighThe actual goal — and the two pull against each other

Returning more documents can only raise recall and tends to lower precision; returning fewer does the reverse. So there is a genuine trade-off, and the design question is where to sit on it. This is also why stemming (Unit 4) is described as "raises recall, can hurt precision" — it is the same axis.

A one-line extra if you want it: F₁ = 2PR/(P+R), the harmonic mean, folds the two into one number. For P = 0.80 and R = 0.24 that is 0.369 — it punishes the weak side, where a plain average (0.52) would hide it. F₁ is not on either slide set, so offer it as an aside rather than as the answer.

IR beyond text: similarity search

Not every collection is text. Similarity search retrieves images, audio, video or faces by comparing features — colour, shape, texture, pitch, rhythm, motion, facial geometry — rather than words. You upload a photo of a flower to TinEye and it returns visually similar images; you record ten seconds of a song and Shazam matches the audio fingerprint against millions of tracks. There is no query "word" anywhere in either process.

B · 4Why is linear scanning (grep) inadequate for IR? How does indexing help?
  • It is slow: every query touches the whole corpus, so cost is O(corpus size).
  • NOT is non-trivial — you must scan the whole document just to prove a word is absent.
  • It can't do proximity queries, because a sequential scan discards word positions.
  • It can't rank results.

Indexing preprocesses documents once, offline, into an inverted index (term → sorted docIDs). A query then touches only the postings of its terms, which supports fast Boolean merges, positional queries and scoring.

A · 2Define precision and recall. A system retrieves 15 documents, 12 of which are relevant, out of 50 relevant documents in the collection. Compute both.

Precision = relevant retrieved ÷ retrieved = 12/15 = 0.80. Recall = relevant retrieved ÷ total relevant = 12/50 = 0.24. Precision measures the accuracy of the result set; recall measures its completeness.

B · 4Why can a system not simply maximise both precision and recall? Illustrate.

They trade off, because the only lever is how many documents you return. Take 1000 documents with 20 relevant.

  • Return all 1000: recall = 20/20 = 100%, precision = 20/1000 = 2%. Perfect recall, useless result set.
  • Return a single relevant document: precision = 1/1 = 100%, recall = 1/20 = 5%. Perfect precision, 19 relevant documents missed.

Each is trivially maximised by degrading the other, so a useful system sits between them. F₁ = 2PR/(P+R) is the usual single-number summary.

Boolean retrieval model

CO1Lec 3–4

The Boolean model is the oldest of the classical models and the simplest thing that could possibly work. It treats a document as nothing more than a set of words — no grammar, no order, no counts. "Brutus agrees to conspire against Caesar" is stored as {brutus, agrees, conspire, against, caesar} and that is all the system knows about it.

A query is a Boolean expression over those words, and the system asks one yes/no question per document: does this document satisfy the expression? This is called exact-match retrieval. There is no "almost matches" and no ordering — every returned document is equally good as far as the model is concerned.

The three operators

Boolean logic has exactly two values, and in IR they mean something concrete: 1 (true) = the term is present in this document, 0 (false) = absent. From that, the operators do what you would expect:

OperatorReturns documents that…EffectExample
AND ∧contain all the termsNarrows the searchPython AND "Machine Learning" — a page with only Python is rejected
OR ∨contain at least one termBroadens the searchPython OR Java — either, or both
NOT ¬do not contain the termExcludesJava NOT Coffee — drops the drink, keeps the language

The truth values are the standard ones: A AND B is 1 only for the row 1,1; A OR B is 0 only for the row 0,0; NOT A simply flips. Operators combine, and parentheses control the order of evaluation — in (AI OR "Machine Learning") AND NOT Robotics the OR is resolved first, then the AND NOT is applied to that result. Getting the parenthesisation wrong changes the answer, which is one of the model's practical weaknesses.

The term–document incidence matrix

To evaluate such a query mechanically you need the presence/absence facts laid out. The term–document incidence matrix does that: one row per term, one column per document, and a 1 where the term occurs.

Read a row and you get a bit-vector for one term across all documents — that is the piece the query operates on. Read a column and you get the set of terms in one document. The query Brutus AND Caesar AND NOT Calpurnia over Shakespeare's plays works like this:

So the whole procedure is three steps, and it is worth writing them out in an exam because that is where the method marks are:

  1. Read off one bit-vector per query term from its row of the matrix.
  2. Apply NOT by complementing — flip every bit of that term's vector.
  3. Combine with bitwise AND / OR column by column, then read the documents whose position holds a 1.

Same matrix, different query. (Antony AND Caesar) AND NOT Brutus → Antony is 110000, Caesar 110111, NOT Brutus 001011. The AND gives 000000… except that Antony also appears in Macbeth, so with the slides' full matrix the answer comes out as Macbeth alone. Always rebuild the vectors from the matrix you are given rather than reusing a remembered answer.

Why the matrix cannot be stored

The matrix is a lovely way to explain the model and a terrible way to implement it. Work through the arithmetic for a modest collection:

N = 1 million documents × ~1,000 terms each → 10⁹ tokens (≈ 6 GB of text)
M = 500,000 distinct terms
matrix size = M × N = 500,000 × 1,000,000 = 5 × 10¹¹ cells
but at most 10⁹ of those cells can be a 1 (one per token)
→ at least 99.8% of the matrix is zeros

You would be spending half a terabyte of cells to store a billion facts. The matrix is extremely sparse, and the fix is the obvious one: stop storing the zeros. Keep, for each term, only the list of documents where it actually appears. That is an inverted index, and it is the subject of Unit 3.

What the model is good and bad at

Advantages

  • Simple to understand and to implement — it is just set operations
  • Fast, once there is an index behind it
  • Precise and predictable: the user knows exactly what the query means, and the same query always returns the same set
  • Gives an expert user fine control, and lets them be sure nothing was silently dropped by a ranker

Limitations

  • No ranking — every hit is equally good, so a 200,000-document result set is unusable
  • Feast or famine: AND tends to return too few documents, OR too many, with little in between
  • Requires the user to guess the exact keywords, and complex nested queries are hard for ordinary users to write
  • Ignores term frequency, so a document mentioning the term once ranks equal to one about nothing else
  • No notion of synonyms or meaning — car will not find automobile
  • Without an index, evaluating it scans every document: O(N × M)

Where it is still used: digital libraries and library catalogues, research-paper and patent databases, legal search (Westlaw has run on Boolean since 1975), medical literature search, enterprise search. The pattern is the same everywhere — trained users, who want a reproducible result set and need to be certain nothing relevant was quietly ranked off the bottom of page one.

B · 3Given an incidence matrix, evaluate (A OR B) AND NOT C.

Write each term's bit-vector from its row. OR the vectors for A and B position by position (1 if either has a 1). Complement C by flipping every bit. AND the two results. Read off the documents whose position holds a 1. Show every intermediate vector — that is where the method marks are.

A · 2Why is the term-document matrix impractical for large collections?

It is huge and almost empty. For 1M documents and 500K terms it is 5×10¹¹ cells, but with only ~10⁹ tokens at most 10⁹ cells can be 1, so at least 99.8% are zeros. Storing only the 1s — one list of docIDs per term — is the inverted index, and it is far more compact.

B · 4State the advantages and limitations of the Boolean retrieval model.

Advantages: simple to understand and implement; fast with an index; exact-match so results are precise and predictable; gives expert users fine control; well suited to library, legal and patent search.

Limitations: no ranking, so large result sets are unusable; feast or famine (AND too few, OR too many); requires exact keywords and hard-to-write nested queries; ignores term frequency so no partial relevance; no synonym or meaning awareness; O(N×M) without an index.

Inverted index & processing Boolean queries

CO1CO2Lec 5–6 + skip-pointer reading

Unit 2 ended with a problem: the incidence matrix is 99.8% zeros. The inverted index is the fix — keep only the 1s. It is the single most important data structure in the course, and almost everything after this unit is either building it, compressing it, or querying it faster.

It has exactly two parts. The dictionary is the sorted list of every distinct term in the collection. Hanging off each dictionary entry is a postings list: the document IDs where that term occurs, sorted by docID. Each individual docID in such a list is called a posting.

Postings can be stored as linked lists (easy to insert into, but you pay pointer overhead) or as arrays (compact and cache-friendly, but awkward to update). The trade-off comes back in Unit 6 when documents start arriving continuously.

Forward index vs inverted index

The name "inverted" is only meaningful against its opposite. A forward index maps each document to the words in it — which is the direction parsing naturally produces. Inverting it means turning every one of those arrows around.

Building it: the four indexer steps

Construction is mechanical, and an exam can ask you to do it by hand on three short documents. The engine of it is a sort.

  1. Tokenize and run the linguistic modules. Friends, Romans, countrymen. becomes the tokens friend roman countryman after normalising and stemming (Unit 4 covers this in detail).
  2. Emit one (term, docID) pair per token. Document 1 emits (friend,1) (roman,1) (countryman,1); document 2 emits its own, and so on. At this point the list is in document order.
  3. Sort by term, then by docID. This is the core indexing step — it is what physically groups all occurrences of a term together. Everything in Unit 6 is about doing this sort when the pair list is too big for memory.
  4. Merge duplicates and split the output. Repeated pairs for the same term and document collapse into one posting (with a frequency count if you are keeping term frequencies). The result is written as two files: a dictionary file of (term, df, pointer) and a postings file.

Answering a query: the merge algorithm

With the index built, Brutus AND Caesar means: fetch both postings lists and compute their intersection. The naive way — for each docID in the first list, search the second — costs O(x·y). Because both lists are sorted by docID you can do far better with two pointers that only ever move forward.

In pseudocode, and with the variants for the other two operators:

All three on one pair of lists. Database = {1,3,5,8}, Security = {2,3,5,7}.

Note that UNION still costs O(x+y) but must visit every posting — you cannot skip anything, because everything ends up in the answer. That fact matters for skip pointers below.

The one thing that makes it all work: both lists are sorted by docID. If they were not, no pointer walk would be possible and you would be back to O(x·y). This is why step 3 of construction sorts by term and then docID.

Query optimisation

For a query with three or more AND terms, the order you combine them changes how much work you do — even though the final answer is identical. The rule is: process terms in increasing document frequency, so the intermediate result stays as small as possible.

Why the order matters. Brutus AND Calpurnia AND Caesar with df values Brutus = 7, Calpurnia = 8, Caesar = 2.

Bad order — (Brutus AND Calpurnia) AND Caesar: the first intersection walks 7 + 8 = 15 postings and might produce up to 7 intermediate results, which you then walk again against Caesar.

Good order — (Caesar AND Brutus) AND Calpurnia: the first intersection walks 2 + 7 = 9 postings and can produce at most 2 results, because an intersection can never be bigger than its smallest input. The second step is then tiny.

This is exactly why df is stored in the dictionary: you know how long a list is before you pay to read it.

For a query that mixes ORs, like (madding OR crowd) AND (ignoble OR strife), you cannot know an OR's size without computing it, so you estimate it as the sum of the dfs of its terms — a conservative upper bound — and then process the ORs in increasing estimated size.

Skip pointers

The merge is already O(x+y), so why go further? Because on a web-scale index a postings list can hold several million entries, and O(x+y) on ten million postings is still ten million steps. Skip pointers make the common case sublinear.

A skip pointer is an extra forward link added at indexing time that lets the walk jump several postings ahead at once. The rule for using one: if the pointer's target is still ≤ the docID you are looking for, you can safely jump, because everything you skipped over was smaller and therefore could not have matched.

Where to put them

  • Heuristic: √P evenly spaced skips for a list of length P.
  • More skips → short spans, so a skip is usable often, but you pay more comparisons and more storage.
  • Fewer skips → long spans that save a lot when taken, but they are rarely takeable.
  • √P is the balance point between those two.

When they don't help

  • OR queries — a union must output every posting, so there is nothing to skip.
  • Intermediate results — they are computed at query time and have no skip pointers built in.
  • Dynamic indexes — skips are easy to place on a static index, hard when postings keep changing.
  • Modern hardware — loading the extra pointers can cost more I/O than the in-memory comparisons they save, so they help less than they used to.

Phrase and proximity queries

A docID-only postings list cannot answer "stanford university" as a phrase. It can tell you both words appear in a document, but not that they were adjacent — so The inventor Stanford Ovshinsky never went to university would be a false hit. About 10% of web queries are phrase queries, so this matters. There are two ways to extend the index.

Biword index

  • Index every consecutive pair of terms as if it were a single vocabulary term: Friends, Romans, Countrymen yields the biwords "friends romans" and "romans countrymen".
  • A two-word phrase is then a single dictionary lookup.
  • A longer phrase becomes an AND of biwords: stanford university palo alto → "stanford university" AND "university palo" AND "palo alto". That needs post-filtering, because a document could contain all three biwords without containing the four-word phrase — a false positive.
  • Extended biwords: POS-tag the text, bucket terms into nouns (N) and articles/prepositions (X), and treat any N X* N string as one term — king of Denmark, catcher in the rye.
  • Rarely used, for two reasons: false positives, and the vocabulary blows up (every pair becomes a term).

Positional index

  • Each posting becomes docID: ⟨pos1, pos2, …⟩ — the word offsets within that document.
  • Answers phrases exactly: for a two-word phrase, look for a position of the second word equal to a position of the first plus one.
  • Also answers proximity queries: employment /4 place finds the two within 4 words of each other. Employment agencies that place healthcare workers is a hit; Employment agencies that have learned to adapt now place healthcare workers is not.
  • Cost: 2–4× the space of a non-positional index, and more work per query.
  • Combination scheme: keep very frequent phrases (Michael Jackson, Britney Spears) as biwords for speed, and handle everything else positionally. Williams et al. (2004) measured this as faster than a pure positional index at a cost of 26% more space.

Westlaw's operator syntax, if it comes up: & = AND, | = OR, % = NOT, " " = phrase, and the proximity family /s (same sentence), /p (same paragraph), /k (within k words).

A · 2Distinguish a forward index from an inverted index.

A forward index maps document → words and answers "what words are in this document?" (D1 → Machine, Learning). An inverted index maps word → documents and answers "which documents contain this word?" (Learning → D1, D2, D3). The forward index is what parsing produces; the inverted index is what queries search, because it lets a query touch only the postings of its terms instead of reading every document.

B · 4Compare term-at-a-time and document-at-a-time query processing.

TAAT processes one term's entire postings list, accumulating partial scores in an accumulator array, then moves to the next term. It is simple, but every candidate document must stay in memory and no score is final until the last term is done.

DAAT advances all postings lists together in docID order and completes one document's score before moving on. It needs less memory and, crucially, a document's score is final as soon as you pass it — which is what makes dynamic pruning (WAND) and early termination possible. Modern engines prefer DAAT for exactly this reason.

C · 6Discuss the techniques used for query optimisation in an IR system.

Lead with the one that carries the marks, then give breadth:

  2. Skip pointers — √P evenly spaced pointers let the merge jump past postings that cannot match.
  3. Boolean re-association — (A AND B) AND C ≡ A AND (B AND C); choose the cheaper grouping.
  4. Query rewriting — synonym expansion to raise recall.
  5. Caching of frequent queries.
  6. TAAT vs DAAT — DAAT is preferred because a score completes as you pass the document, which enables ranking and pruning.

  8. Early termination — stop once the top-10 is settled.

Document & term processing

CO1CO2Lec 7–9

Unit 3 assumed two things it had no right to assume: that we know what a document is, and that turning it into a list of terms is obvious. Neither is true. This unit is everything that happens between "here is a pile of files" and "here is a clean list of dictionary terms".

Document delineation: what counts as one document?

Delineation is finding the boundaries — where one document ends and the next begins — and giving each one a docID. Part of the job is settling the format (pdf, docx, html), the language, and the character encoding; each is really a classification problem, though in practice heuristics do the work.

The harder part is choosing the document unit, and there is genuinely no right answer. Is a document a file? An email? An email with five attachments — one document or six? A book, or each of its chapters? A single XML file holding 10,000 news articles is 10,000 logical documents inside one physical file. It is a design decision with consequences you will feel in Unit 7's scoring.

Three kinds of delineation

  • Physical — explicit markers do the work: <doc>…</doc> tags, page breaks, chapter breaks, file boundaries.
  • Logical — inferred from the content's own structure: headings, titles, section numbers, paragraph patterns.
  • Automatic — ML/NLP boundary detection, needed for crawled pages, email threads, log streams and OCR scans where there are no reliable markers at all.

Granularity: how big should a document be?

Suppose you index a 400-page textbook as one document. Two things go wrong. First, dilution: even if the query term appears ten times, that is ten occurrences among 150,000 words, so its weight is washed out and a short, focused article beats the book. Second, the user wanted the paragraph that answers their question, not a 400-page PDF download.

Go too far the other way — index single sentences — and you get precise matches that have lost all their context. That is the granularity trade-off: fine granularity is precise but context-free; coarse granularity keeps context but adds noise. The middle ground has three standard techniques:

  • Static passage retrieval — pre-cut documents into uniform chunks before indexing (a common setting is 256–512 tokens with about 10% overlap so a sentence spanning a boundary is not lost), or cut on logical sections.
  • Dynamic passage retrieval — index whole documents, but at query time slide a window over the text and score the density of query terms inside it, returning the best window.
  • TextTiling — find natural boundaries by computing cosine similarity between adjacent blocks of tokens; a dip in that similarity means the topic just changed, so cut there.

This is the same problem modern RAG systems call "chunking", which is why the second slide set frames it that way.

Getting readable text out of the file

  • Encoding: input arrives as ASCII, UTF-16, ISO-8859-1 or a regional encoding and must be normalised to UTF-8. Unicode then has two normal forms: NFD decomposes é into e plus a combining acute accent, NFC recomposes it into a single character. Pick one and apply it consistently before you sort or compare terms, or identical-looking words will not match.
  • HTML/XML stripping: remove the tags, but replace block-level ones with a newline. Strip </h1> naively and <h1>Header</h1>Content becomes the junk term HeaderContent.
  • OCR: scanned documents introduce systematic character errors — cl read as d, rn read as m. This is exactly the damage that tolerant retrieval (Unit 5) exists to repair.

Tokenization: harder than splitting on spaces

Tokenization turns a character stream into tokens. The naive rule "split on whitespace and punctuation" fails constantly, and the failures are the examinable content.

In English

  • Apostrophes: O'Neill → oneill, o'neill, o+neill? aren't, India's have the same problem.
  • Hyphens: Hewlett-Packard is probably two tokens, co-education probably one, and state-of-the-art is anyone's guess. the hold-him-back-and-drag-him-away manoeuvre makes the point.
  • Multi-word names: San Francisco and New Delhi are one concept in two tokens. Worse, York University vs New York University — splitting makes them overlap.
  • Numbers and dates: 3/20/91, 20/3/91, Mar 20 1991, B-52, 100.2.86.144, (800) 234-2333. Older systems dropped them; modern ones index them, often as separate metadata, because error codes and IPs are genuinely searched for.

In other languages

  • Chinese and Japanese have no spaces at all, and the segmentation can be genuinely ambiguous — two characters may be one word meaning "monk" or two words meaning "and" + "still".
  • German, Dutch, Swedish form compounds: Computerlinguistik = Computer + Linguistik; Lebensversicherungsgesellschaftsangestellter needs a compound splitter.
  • Arabic, Hebrew, Urdu are written right to left but embed left-to-right numbers, so text is bidirectional. Unicode handles it, but the renderer must cooperate.
  • French elision: L'ensemble — is that l, l', or le? You want it to match un ensemble.

Normalization: making variants match

The goal is that a query term and a document term that mean the same thing end up as the same dictionary entry. The main technique is defining equivalence classes — deciding, say, that deleting periods makes U.S.A. and USA the same term, or that résumé and resume collapse together. The guiding criterion is always practical: how are users likely to type this? (Usually without the accents.)

The alternative is asymmetric expansion, where the mapping depends on what was typed:

query window  → searches window, windows
query windows → searches Windows, windows
query Windows → searches Windows only

More powerful, because the user's capitalisation carries information (the operating system vs the thing in a wall). Less efficient, because there is no single dictionary entry — the query has to fan out.

  • Case folding — lowercase everything. It is wrong for MIT vs mit (German for "with"), Fed vs fed, SAIL vs sail, General Motors — but users type in lowercase regardless of correctness, so lowercasing everything usually wins.
  • Stop words — the extremely common words (a, an, and, are, as, at, be, by, for, from, the, to, was, with). The top 30 words are roughly 30% of all postings, and they carry almost no meaning, so older systems removed them. The trend is now against removing them, because you need them for phrase queries ("King of Denmark", "President of India"), for titles ("Let it be", "To be or not to be") and for relational queries ("flights to Bangalore"). Compression and good query optimisation make keeping them affordable. Most web engines index them.
  • Thesauri handle semantic equivalence (car = automobile) by hand-built equivalence classes — either index a document containing automobile under car as well, or expand the query. Soundex (Unit 5) does the same for phonetic equivalence (Muller = Mueller).

The two morphology types are worth naming: inflectional changes grammatical form without changing the word (cutting → cut); derivational changes the word class (destruction → destroy). Stemming does both, often too eagerly.

Does it actually help? Stemming raises recall and can hurt precision — the same trade-off as Unit 1. It helps [tartan sweaters] (merging sweater/sweaters) and [sightseeing tour san francisco]. It hurts [operational AND research], [operating AND system] and [operative AND dentistry], because Porter maps operate, operating, operational, operative, operation, operatives all onto the single stem oper — so "operational research" and "operating system" become the same query.

Two named error types

Over-stemming false positive

Unrelated words collapse onto the same root. organization and organ both → organ; university → universe; policy → police. You now retrieve documents about organs for a query about organisations, so it hurts precision.

Under-stemming false negative

Forms of the same word fail to merge. european and europe stay separate entries, so a search for one misses documents using the other. It hurts recall.

A stemmer is tuned by trading one against the other — chop more aggressively and over-stemming rises, chop less and under-stemming does. Morphological processing is the principled alternative: analyse a word into prefix + root + suffix (unhappiness → un + happy + ness; rewriting → re + write + ing), so that compute, computer, computing, computation, computational all reach compute for the right reason. Full morphological analysis gives only modest retrieval benefit for the cost, which is why crude stemmers survive.

The Porter stemmer

The standard English stemmer. Its structure: five phases applied in sequence, each phase a set of condition → action rules. Two conventions matter — within a compound command the rule matching the longest suffix wins, and only one rule per step may fire.

The conditions are tested on the stem that would remain, not the whole word. That trips people up:

  • Measure m — the number of vowel-consonant sequences in the pattern [C](VC)m[V]. It is a rough measure of word length: tree has m = 0, trees and oak have m = 1, private has m = 2. A rule written (m>1) only fires on longer words, which protects short ones from being destroyed.
  • *S — the stem ends in the letter S. *v* — the stem contains a vowel. *d — the stem ends in a double consonant.
Step 1a: SSES→SS (caresses→caress)  IES→I (ponies→poni)  SS→SS (caress)  S→∅ (cats→cat)
Step 1b: (m>0) EED→EE (agreed→agree, feed→feed)  (*v*) ED→∅ (plastered→plaster)  (*v*) ING→∅ (motoring→motor, sing→sing)
Step 1c: (*v*) Y→I (happy→happi, sky→sky: no vowel in "sk")

Read two of those rules carefully, because they show the conditions doing real work.

(m>0) EED → EE: agreed leaves the stem agr, which has m = 1 > 0, so the rule fires and gives agree. feed leaves the stem f, which has m = 0, so the rule does not fire and feed stays as it is. Without that guard you would stem feed to fee.

(m>1) EMENT → ∅: replacement leaves replac with m = 2, so it fires → replac. cement leaves c with m = 0, so it does not → cement survives intact.

Your slide writes "sky → ski" under step 1c. By the rule's own (*v*) condition the remaining stem "sk" contains no vowel, so the rule should not fire and sky stays sky. If this comes up, give the rule-based answer and say why.

The other stemmers worth naming are Lovins (a single pass, longest-suffix removal, about 250 rules), Paice, and Snowball (Porter's own later framework). They differ in aggressiveness — on the same sentence Lovins produces analys, reve, vis where Porter produces analysi, reveal, visibl.

Dictionaries & tolerant retrieval

How the dictionary is stored, and why it matters

Lec 10 has no slides among your uploads, so this part follows Manning §3.1.

The dictionary must answer "does this term exist, and where are its postings?" millions of times a second. Two families of structure do that, and they differ on exactly one question that turns out to be decisive: does the structure keep terms in order?

Hash table

  • O(1) average lookup — the fastest thing there is for an exact term
  • Collisions must be handled
  • No prefix search, and minor variants (resume / résumé) hash to unrelated slots
  • Must be rehashed as the vocabulary grows

Search tree (binary / B-tree)

  • O(log M) lookup, provided the tree stays balanced
  • Supports prefix and range queries
  • A plain binary tree needs constant rebalancing; a B-tree lets each internal node hold between a and b children (say [2,4]), which collapses the number of levels, matches disk block sizes, and rebalances far less often
  • Needs a total ordering of characters, which is awkward across scripts

Trie / TST / FST

  • A trie (or ternary search tree) branches on characters from the root, with marked nodes ending terms. Lookup is O(term length) and prefix search is native — the prefix is the path
  • An FST / DAWG is a directed acyclic graph that shares prefixes and suffixes, so it is dramatically more compact. This is what Lucene actually uses
  • A sorted array is the simple middle ground: O(log N) binary search, prefix-friendly, but costly to insert into

The permuterm index

The trick is beautifully simple. A B-tree can only find a * at the end. So: store every rotation of every term, and then rotate the query until its * lands at the end.

The k-gram index

The other approach: chop every term into overlapping k-character pieces and index those. With $ marking the boundaries, the bigrams of april are $a ap pr ri il l$. A separate index maps each k-gram to the terms containing it.

A wildcard becomes a Boolean query over k-grams: mon* → $m AND mo AND on. But this only narrows the candidates — it does not guarantee correctness. red* → $r AND re AND ed also matches retired, which contains all three bigrams in the wrong places. So you must post-filter: take the candidate terms, check each against the original wildcard pattern, and discard the impostors.

Permuterm vs k-gram in one line: permuterm is a single lookup with no filtering but costs ~4× the dictionary; k-gram uses far less space but needs a generate-then-filter step. That trade — space against post-processing — is the answer a comparison question wants.

Spelling correction

Two distinct jobs. Correcting documents handles OCR damage (the cl/d and rn/m confusions from Unit 4) before indexing. Correcting queries is the "Did you mean…" box, and it is the one exams ask about.

Two levels of ambition:

  • Isolated-word correction checks each word against the lexicon on its own. It fixes recieve → receive, but it cannot fix I flew form Heathrow, because form is a perfectly good word.
  • Context-sensitive correction looks at the surrounding words, which is what catches form → from.

The lexicon you check against can be a standard dictionary, a domain-specific one, or simply the corpus's own vocabulary (which handles proper nouns and jargon for free). Closeness is then measured by edit distance, weighted edit distance, or k-gram overlap.

Edit (Levenshtein) distance

The minimum number of single-character insertions, deletions and substitutions to turn one string into another. Computed by dynamic programming over a grid: cell D[i,j] is the distance between the first i characters of the source and the first j of the target.

D[i,0] = i  (delete all i characters) ;  D[0,j] = j  (insert all j characters)
D[i,j] = min( D[i-1,j]+1 delete,   D[i,j-1]+1 insert,   D[i-1,j-1] + (0 if Xᵢ=Yⱼ else 1) substitute / free match )

Fill the grid left to right, top to bottom; the answer is the bottom-right cell. Each cell only looks at three neighbours — above, left, and diagonal — which is the whole algorithm.

Cutting the candidate set down

You cannot compute edit distance against all 400,000 dictionary terms for every query word. So you generate a small candidate set cheaply, then run the expensive test only on those. The standard filter is k-gram overlap, scored with the Jaccard coefficient:

Jaccard(X, Y) = |X ∩ Y| / |X ∪ Y|    (0 = no overlap, 1 = identical)

Set a threshold, keep the terms above it, and only then compute edit distance on the survivors. Other cheap heuristics: restrict to terms with the same first letter (most typos don't hit character one), or use permuterm rotations.

Why context-sensitive correction is expensive. Take the query flew form Heathrow, with 7 plausible corrections for flew, 19 for form and 3 for heathrow. Trying every combination means 7 × 19 × 3 = 399 candidate phrases to score. Fixing only one word at a time — hold the others as typed — drops it to 7 + 19 + 3 = 29. Better still: break the phrase into biwords and correct one term per biword. Because even 29 is costly, systems typically run spelling correction only when the original query returned few or no results.

C · 6Compare the permuterm and k-gram indexes for m*n and fi*mo*er.

Permuterm: m*n rotates to n$m* — a single prefix lookup, exact, no filtering. fi*mo*er has two stars, so rotate on the outer pair to get er$fi*, then post-filter the candidates for "mo" appearing in the right place.

Bigram: m*n → $m AND n$, then post-filter. fi*mo*er → $f AND fi AND mo AND er AND r$, then post-filter (fishmonger passes; a term with those bigrams in the wrong order fails).

Permuterm is faster and needs less filtering but costs about 4× the dictionary; k-gram uses far less space but always needs a generate-then-filter step.

A · 2Why can't a hash table serve wildcard queries?

Hashing deliberately scatters lexically adjacent terms into unrelated buckets, so there is no way to enumerate every term sharing a prefix. A B-tree keeps terms in sorted order, so a prefix is a contiguous range and one walk returns all of them; a trie or FST goes further and makes the prefix a path from the root.

B · 3Why is *ing hard on a normal B-tree, and how do you fix it?

A B-tree orders terms by their start, so words ending in ing (computing, reading, running) are scattered across the whole tree with no contiguous range to walk. Fix it either with a reverse B-tree holding every term backwards (then look up gni*) or with a permuterm index (look up ing$*).

B · 4Compare the dictionary data structures available for an IR system.

Hash table: O(1) average exact lookup, but entries are unsorted so no prefix or wildcard search, and it must be rehashed as the vocabulary grows. Sorted array: O(log N) binary search and prefix-friendly, but insertion is costly. BST / B-tree: O(log M), ordered so it supports range and prefix queries and handles a dynamic collection; a B-tree keeps the tree shallow which suits disk blocks. Trie / ternary search tree: O(term length), prefix search is native, so it is the structure of choice for comput*. FST / DAWG: a directed acyclic graph sharing prefixes and suffixes — very compact and prefix-friendly.

The examinable trade-off is hashing against all the rest: fastest for exact lookup, but it destroys the adjacency that tolerant retrieval needs.

Index construction

CO2Lec 13–16

Unit 3 said "sort the (term, docID) pairs" as if that were a single step. For a real collection it is not, because the pairs don't fit in memory and sorting on disk is catastrophically slow if you do it naively. This unit is about doing that sort properly, and then about keeping the index up to date once documents start arriving continuously.

Hardware basics: why any of this is hard

Everything here follows from one fact: disk is about 10⁶ times slower than memory. So the design goal is never "fewer operations" — it is "fewer disk seeks".

  • Memory hierarchy, fastest to slowest: registers → cache (SRAM) → DRAM → disk/SSD → tape.
  • Standard parameters for calculations: seek s = 5 ms, transfer b = 0.02 µs per byte, CPU operation p = 0.01 µs. Total access time = seek + rotational latency + transfer.
  • The OS reads whole blocks (8–256 KB), so reading one byte costs the same as reading a block. Always read into a buffer and work from there.
  • Corollary that surprises people: reading compressed data and decompressing it in memory is faster than reading the raw data, because the CPU time is trivial next to the I/O saved.
10 MB read contiguously: 10⁷ bytes × 2×10⁻⁸ s + 1 seek = 0.2 + 0.005 = 0.205 s
Same 10 MB in 100 scattered chunks: 0.2 + 100 × 0.005 = 0.7 s  — about 3.4× slower
The transfer time is identical. The 99 extra seeks are the entire difference.

The benchmark collection, RCV1 (Reuters), is worth memorising because every numerical uses it: N = 800,000 documents, average 200 tokens each, M = 400,000 distinct terms, T = 100 million tokens, about 1 GB of text.

The scaling problem, in one line. At 8 bytes per (termID, docID) pair, T × 8 = 800 MB of intermediate data — for a 1 GB collection. That does not fit in the RAM of a typical machine, so you cannot just sort it. Hence external sorting.

Note also why termIDs are used instead of the term strings: a termID is 4 bytes, fixed length, and comparable in one instruction; an average English term is about 7.5 bytes, variable length, and needs a string comparison. Over 100 million pairs that difference dominates.

BSBI: Blocked Sort-Based Indexing

The idea is divide and conquer. Chop the collection into blocks sized to fit in memory, sort each block in memory, write the sorted block to disk, then merge the sorted blocks together — which can be done with sequential reads.

Why the merge is cheap. Every block file is already sorted, so the merge only ever reads forwards. One read buffer per file plus one write buffer turns what would be random disk access into sequential streaming — and sequential is the only kind of disk access that is fast.

The min-heap holds one entry per open block file: the smallest termID that file currently offers. Pop the minimum, concatenate that term's postings from every block that has it, write them out, then refill the heap from the file you just popped. Each heap operation is O(log n) for n blocks, which is negligible next to the I/O.

BSBI(collection)
  n ← 0
  while (docs remain)
     n ← n+1
     block ← PARSENEXTBLOCK()          // accumulate (termID, docID) pairs until the block is full
     BSBI-INVERT(block)                // sort the pairs in memory, group into postings lists
     WRITEBLOCKTODISK(block, fₙ)
  MERGEBLOCKS(f₁…fₙ ; f_merged)        // k-way merge with a min-heap
  • Complexity Θ(T log T), dominated by the sort. In practice parsing and merging — that is, I/O — dominate the wall-clock time.
  • Its limitation: BSBI needs a global term → termID mapping held in memory throughout. For a 400,000-term vocabulary that is fine; for web-scale vocabularies it is not.

SPIMI: Single-Pass In-Memory Indexing

SPIMI removes the sort and the global termID map in one stroke. Instead of emitting (termID, docID) pairs and sorting them later, it uses the term string itself as a hash key and appends the docID directly onto that term's postings list as it goes.

Dynamic indexing: documents keep arriving

Everything above builds an index once, from a fixed collection. Real collections change — pages are added, edited and deleted — and rebuilding from scratch on every change is obviously impossible. But so is editing the index in place: a postings list sits in the middle of a huge disk file, and inserting one docID into it would mean shifting everything after it.

The standard answer is the auxiliary index:

  • Keep the big main index on disk, untouched. Keep a small auxiliary index in memory for newly arrived documents.
  • A query searches both and merges the results.
  • Deletions can't remove postings, so they go in an invalidation bit vector — one bit per document — and results are filtered through it before being returned. An update is therefore a delete plus a re-insert.
  • When the auxiliary index reaches n postings, merge it into the main index and start a fresh one.

The cost problem. Each merge rewrites the entire main index. Over T total postings you do T/n merges, and the k-th one rewrites about kn postings — so the total work is Θ(T²/n), quadratic. For large T that is ruinous.

Logarithmic merging

The fix is to stop merging everything into one place. Keep a series of indexes I₀, I₁, I₂ … of geometrically growing sizes n, 2n, 4n, 8n. When the in-memory Z₀ fills, it doesn't join the big index — it tries to become I₀. If I₀ is already occupied, the two merge into a size-2n index that tries to become I₁, and so on up the chain. It behaves exactly like carrying in binary addition.

This is exactly how Lucene, Elasticsearch and Solr work, where the indexes are called segments. Documents become searchable immediately after indexing, because the newest segment is searched along with the rest.

Why not simply keep one file per postings list, and edit the one you need? Because file systems choke on millions of tiny files. And why not one giant file? Because then every merge rewrites the whole thing — which is the Θ(T²/n) problem you were trying to escape.

Distributed indexing

At web scale even SPIMI on one machine fails, so the index is split across many. There are exactly two ways to split it, and the distinction is examinable:

Document partitioning

Each machine holds a complete index over a subset of the documents. Every query is broadcast to every machine and the partial results are merged.

Simpler, and resilient — if a machine dies you lose some documents, not some terms, so results degrade gracefully. This is the usual choice in practice.

Term partitioning

Each machine holds all postings for a subset of the terms. A query only touches the machines holding its terms.

Sounds cheaper, but a multi-term query must ship whole postings lists between machines to intersect them, which is usually worse than broadcasting the query.

MapReduce (Dean & Ghemawat, 2004 — used by Google and Hadoop) builds the index in two phases, and its reduce phase is term partitioning:

  1. Map (parsers). Input is split into 64 MB chunks. Each parser reads its chunk and emits (term, docID) pairs, writing them into local segment files partitioned by key range — say a–f, g–p, q–z.
  2. Reduce (inverters). Each inverter is assigned one key range. It collects the segment files for that range from every parser, sorts them, and writes the final postings for those terms.

Because machines in a large cluster fail routinely, the framework handles it three ways: reassignment (if a parser dies, the master hands its split to another machine), immutable segment files (map output is write-once, so re-running a task can never leave a half-written mess), and checkpointing of the map phase's state. That is what makes petabyte-scale indexing possible on cheap hardware that is expected to break.

Security and access control lists

In enterprise search, not every user may see every document — managers can open Salaries.pdf, interns cannot. Filtering after the fact is not enough; the restriction has to be part of query processing. The structure used is pleasingly familiar.

The structure

  • Build a user–document access matrix: rows = users, columns = documents, cell (i,j) = 1 if user i may read document j.
  • That is the same shape as the term–document incidence matrix of Unit 2, with users in place of terms.
  • So invert it the same way: each user gets an ACL postings list of the documents they can access — User_Alok → [doc5, doc7, doc9].

At query time

  1. Run the text search → candidates [doc5, doc6, doc9].
  2. Fetch the user's ACL list → [doc5, doc7, doc9].
  3. Intersect them with the ordinary merge algorithm → [doc5, doc9].

Security becomes just one more AND clause, using machinery you already have.

Challenges: an administrator's ACL may cover millions of documents, making that intersection the slowest part of the query; and permissions change constantly, which is the dynamic-indexing problem all over again. The common workaround is to check permissions at the file-system level during final retrieval instead of inside the index.

Parametric/zone indexes, tf-idf & vector space scoring

CO3Lec 19–22

Every unit so far has answered a yes/no question: does this document match? This unit replaces that with a number, so documents can be ordered. It is the heaviest-weighted part of the paper (CO3 is "analyse", so expect a full numerical plus a "why did it come out that way" part).

Why ranked retrieval

Boolean search is feast or famine. The slides' example: the query standard user dlink 650 returns 200,000 hits — unusable. Add two words, standard user dlink 650 no card found, and it returns 0. There is no middle setting, and finding it requires a skilled user who understands the collection.

Ranked retrieval changes the contract. The query is free text, every document gets a score in [0,1], and only the top k are shown. A large result set is no longer a problem, because the user never sees past position 10 — provided the ranking is good. That proviso is the rest of the unit.

Parametric and zone indexes

Before scoring the text, note that documents have structure worth exploiting. Two kinds:

Parametric index

Structured metadata fields with a small, finite set of values — author, year, language, format. Queries filter on exact values: Author = Shakespeare AND Year = 1601 intersects the two field postings lists, exactly like a Boolean AND.

Zone index

Regions of arbitrary free text — title, abstract, body. You can encode the zone in the dictionary (merchant.title → D1) or in the postings (merchant → D1.title, D1.body). The second keeps the dictionary smaller and makes weighted scoring easier.

Zones matter because a match in the title is worth more than one buried in the body. Weighted zone scoring makes that explicit: give each zone a weight, and sum the weights of the zones that matched.

Score(q,d) = Σᵢ gᵢ · sᵢ   where Σ gᵢ = 1 and sᵢ ∈ {0,1} (did zone i match?)
Slide weights: Author 0.2 · Title 0.3 · Body 0.5

A document matching in title and body only: 0.3 + 0.5 = 0.8
A document matching in author only: 0.2

A careful reading of the slide's worked example: D1's title is "Merchant of Venice" and its author is "William Shakespeare", so the query shakespeare actually matches the author and body zones, giving 0.2 + 0.5 = 0.7. The slide marks Title = yes, Author = no and reports 0.8. Show the zone table and your reasoning and you earn the method marks either way. A cleaner check from the same slide: with Title 0.4 and Body 0.6, a match in the title alone gives 0.4.

Scoring the text itself

Attempt 1: the Jaccard coefficient

The simplest overlap measure, reused from Unit 5: Jaccard(q,d) = |q ∩ d| / |q ∪ d|. It is a sensible starting point and fails in three instructive ways.

Query ides of march. D1 = "caesar died in march", D2 = "the long march".

D1: intersection = {march} = 1, union = 6 → 1/6 ≈ 0.167. D2: intersection = 1, union = 5 → 1/5 = 0.2.

So D2 wins — purely because it is shorter, not because it is more relevant. That is the failure mode.

  • It ignores term frequency. A document mentioning march once scores the same as one mentioning it twenty times.
  • It ignores rarity. Matching on the counts as much as matching on calpurnia, though only one of those tells you anything.
  • Its length normalisation is crude. Dividing by the union punishes long documents indiscriminately.

The next three ideas fix those three problems in order.

Fix 1: term frequency, damped by a log

Count how often the term appears in the document — but not linearly. A document with 10 occurrences of car is more about cars than one with 1 occurrence, but it is not ten times more about cars. So take a log:

w = 1 + log₁₀(tf)  if tf > 0, else 0

tf = 1 → w = 1  ·  tf = 2 → w = 1.3  ·  tf = 10 → w = 2  ·  tf = 1000 → w = 4

Ten times the count buys you twice the weight; a thousand times buys four times. That saturation is the entire point.

Fix 2: inverse document frequency, for rarity

Rare terms are informative; common ones are not. If a query contains arachnocentric, a document containing it is almost certainly relevant. If it contains the, that tells you nothing — which is the same intuition that motivated stop words in Unit 4, now expressed as a weight instead of a deletion.

Fix 3: the vector space model, and length normalisation

Developed by Gerard Salton in the 1960s. Every term in the vocabulary becomes a dimension, so a document is a point in |V|-dimensional space whose coordinates are its tf-idf weights. The query is a point in the same space. The space is enormous and almost entirely empty — most documents have a non-zero coordinate on only a few hundred of the 400,000 axes.

Boolean asked "does this document match?". The vector space model asks "how close is it?" — and the obvious answer, distance, turns out to be wrong.

Ranking by increasing angle is the same as ranking by decreasing cosine, because cosine falls monotonically over 0° to 180°. So you never compute the angle itself — just the cosine.

‖x‖₂ = √(Σ xᵢ²)    unit (length-normalised) vector = x / ‖x‖₂

cos(q,d) = (q · d) / (‖q‖ ‖d‖) = Σ qᵢdᵢ / (√Σqᵢ² · √Σdᵢ²)

For vectors already length-normalised, this collapses to just the dot product:  cos(q,d) = q · d

Normalising the vector to unit length is the fix for document length — it is what pushes d and d′ onto the same point on the unit sphere.

Bag of words. The vector records which terms appear and how often, not their order, so "John is quicker than Mary" and "Mary is quicker than John" have identical vectors. This is the same thing as assuming term independence, and it is the model's biggest known weakness — along with having no semantics at all (car ≠ automobile) and a dimensionality of |V|.

A · 2Jaccard score of the query "ides of march" against D1 "caesar died in march" and D2 "the long march".

D1: ∩ = {march} = 1, ∪ = 6, so 1/6 ≈ 0.167. D2: ∩ = 1, ∪ = 5, so 1/5 = 0.2. D2 ranks higher only because it is shorter, which exposes Jaccard's three weaknesses: no term frequency, no rarity weighting, and crude length normalisation.

B · 4Why use cosine similarity rather than Euclidean distance? Include the d / d′ argument.

Euclidean distance grows with vector length, and long documents have long vectors. Take d′ = document d with its own text appended: the content and term distribution are identical, so d′ is exactly as relevant as d — but the Euclidean distance from the query to d′ is large, so distance would rank it far worse. The angle between d and d′ is 0 (cosine 1), because they point in the same direction.

Cosine is the dot product of the length-normalised vectors, so it measures direction — the term distribution — and discards magnitude — the document length. That makes long and short documents comparable, which is exactly what ranking needs.

A · 2Parametric vs zone index.

A parametric index covers structured metadata fields with a finite set of values (year, author, language), and is used for exact filtering. A zone index covers regions of arbitrary free text (title, abstract, body), and is used for region-specific search and for weighted zone scoring, where a match in a more important zone contributes more to the score.

B · 4Why does tf use a log, and why does idf use a log? Why is df preferred to cf?

Log on tf: 10 occurrences make a document more relevant than 1, but not 10× more relevant, so the weight must saturate. 1+log₁₀ gives 1, 2, 4 for tf of 1, 10, 1000.

Log on idf: N/df spans six orders of magnitude, so the log dampens it into a usable range. The base is irrelevant for ranking, since it scales all scores equally.

df over cf: insurance (cf 10,440, df 3,997) and try (cf 10,422, df 8,760) occur almost equally often overall, but insurance is concentrated in far fewer documents, which makes it much more discriminating. Only df captures that concentration.

B · 4State the advantages and limitations of the vector space model.

Advantages: ranked retrieval rather than a flat set; partial matching, so a document need not contain every query term; similarity is a simple and efficient computation; accepts free-text natural-language queries; length normalisation makes documents of different sizes comparable.

Limitations: very high dimensionality (|V| can be 400,000); no semantics, so car ≠ automobile; assumes term independence (the bag-of-words assumption), so word order and relationships are ignored; computationally expensive at scale without optimisation.

Slide errata & traps

These are places where a slide disagrees with the textbook or with its own arithmetic. If one comes up in the exam, show the working and state the convention you're using. That protects your marks whichever version the examiner expects.

BSBI block size. One slide says "limit the block to 1 GB (10 million pairs)". But 1 GB ÷ 8 B is 125M pairs, and with that many pairs RCV1 fits in a single block. The "10 blocks" answer only follows if a block holds 10M pairs, which is 80 MB. Use whatever block capacity the question gives.
Permuterm rotations. The slide lists 5 rotations for hello and leaves out $hello. The book (and the same slide's "m+1 rotations") gives 6.
Weighted zone example. The slide's match column (Title=yes, Author=no) doesn't fit D1's actual text for the query "Shakespeare". See the note in Unit 7.
Edit-distance pseudocode. The slide labels D[i-1,j] as "insert" and D[i,j-1] as "delete". Relative to transforming the source into the target, those labels are swapped. With unit costs the numbers come out the same, so just be consistent.
lnc.ltc wording. One slide line says the query uses "no normalization", but the c in ltc means cosine, and the worked table does normalize the query (0.34, 0.52, 0.78). Normalize.
Soundex variant. Your slides (and Manning) code h, w and y as 0, like vowels. The "official" American Soundex treats h and w differently, so some online calculators give different codes. Follow the slide table.
Porter 1c. "sky → ski" breaks the (*v*) condition. See Unit 4.
